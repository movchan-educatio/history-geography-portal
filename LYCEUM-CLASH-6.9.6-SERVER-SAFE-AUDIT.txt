ЩО БУЛО НЕ ТАК

Старий bellClashStartRoom робив runTransaction() НА ВСІЙ КІМНАТІ та всередині:
• змінював HP/score/alive/invulnerableUntil КОЖНОГО реального гравця;
• створював players/BOT_2, BOT_3 тощо;
• змінював room.status.

Це пояснює симптом:
• HOST міг побачити локальний optimistic Firebase event і потрапити у гру;
• другий пристрій залишався у lobby, бо сервер міг відхилити transaction через validation/rules для чужого UID або BOT_X.

Тобто проблема була не в тому, що другий телефон "не ловив" status.
Ймовірно status взагалі НЕ ПІДТВЕРДЖУВАВСЯ сервером.

4. SERVER CONFIRMATION
Після update() виконується get(.../status).
HOST не входить у матч, доки сервер реально не підтвердив "playing".

Це прибирає оманливий optimistic start.

5. КОЖЕН ГРАВЕЦЬ ІНІЦІАЛІЗУЄ ТІЛЬКИ СЕБЕ
Коли клієнт входить у матч, bellClashWritePlayer пише у власний UID:
• spawn x/y;
• hp/maxHp;
• alive;
• score/deaths;
• invulnerableUntil.

Тобто користувач A не переписує дані користувача B.

6. БОТИ НЕ СТВОРЮЮТЬСЯ У START TRANSACTION
Вони залишаються local-authoritative через існуючий bellClashGuaranteeSoloBots().
Firebase sync BOT_X — лише best effort і не може блокувати старт матчу.

7. ДРУГИЙ ГРАВЕЦЬ
Після Join запускається окремий onValue на:
lyceumClashRooms/CODE/status

Як тільки сервер реально показує "playing":
• клієнт читає кімнату;
• знаходить свій UID;
• відкриває battle screen.

8. HOST
Після успішного server-confirmed StartRoom HOST також читає кімнату і входить через той самий bellClashLoadServerMatch().
Тобто HOST і JOINED PLAYER мають ОДИН шлях входу.

9. РУЧНА СТРАХОВКА
