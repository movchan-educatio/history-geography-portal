LYCEUM CLASH 7.6 — ROOM STABLE

ЩО ПОКАЗАВ СКРІНШОТ 7.5
Кнопка вже перейшла у «СТВОРЮЮ…», отже onclick та create UI працюють.
Вона не повернулася у success/error, отже завис один із await усередині room create.

У 7.5 був конкретний недолік:
fetch() мав AbortController, АЛЕ перед fetch виконувався:
await auth.currentUser.getIdToken()

Цей getIdToken НЕ мав timeout.
Якщо Firebase Auth зависав при отриманні/оновленні токена, AbortController ще навіть не створювався.
Тому екран міг висіти необмежено.

ЩО ЗМІНЕНО

1. TOKEN TIMEOUT
getIdToken() тепер максимум 3 секунди.
Спочатку використовується вже кешований Firebase access token, якщо він є.

2. ПОВЕРНУТО ВІДОМИЙ РОБОЧИЙ CREATE PATH
Першою спробою кімната створюється через звичайний:
set(roomRef, payload)

Саме такий механізм створював кімнати у попередніх робочих версіях.

3. SDK WATCHDOG
SDK set має максимум 4.2 секунди.
Якщо confirmation завис — код НЕ чекає вічно.

4. HTTPS FALLBACK
Після SDK timeout автоматично виконується HTTPS PUT у ТОЙ САМИЙ code з тим самим payload.
Якщо SDK-запис просто запізнився, подвійний запис не шкодить, бо дані однакові.

5. ABSOLUTE UI WATCHDOG
Весь процес create room має максимум 11.5 секунди.
Після цього кнопка ОБОВ'ЯЗКОВО повертається зі стану «СТВОРЮЮ…» та показує конкретну помилку.

6. ПОКРОКОВИЙ СТАТУС
Під кнопкою видно етап:
• підготовка
• Realtime SDK…
• HTTPS fallback…
• готово / помилка

7. ТОЧНІ ПОМИЛКИ
ROOM_TOKEN_TIMEOUT — Auth завис на токені.
ROOM_PERMISSION — Firebase Rules блокують запис.
ROOM_HTTP_TIMEOUT — Firebase REST не відповідає.
ROOM_UI_TIMEOUT — весь create перевищив 11 секунд.
ROOM_CREATE_BOTH_FAILED — не спрацювали обидва транспорти.
